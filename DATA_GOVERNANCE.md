# Data Governance

This document defines two related but distinct things, and it is important
not to confuse them:

1. **How this repository itself must be governed** (the meta-rule: this
   codebase is a teaching artifact and must never contain real sensitive
   data).
2. **How the platform this repository builds governs data** (the product
   behavior: how a deployed instance of this platform would classify, mask,
   certify, and control access to test data in a real organization).

## Part A — Governance of this repository's own content

### A.1 Synthetic data only

Every example, fixture, seed script, or screenshot in this repository must
use synthetic data. "Synthetic" means generated or fabricated for the
purpose of this project — not a real record with names changed, not a
public dataset that happens to contain real people, not sample data copied
from any real organization's system.

Approved sources for example data in this repository:
- Data generated by the platform's own synthetic data generator (once
  built, in later phases)
- Hand-authored fixtures using obviously fictitious values (e.g., patient
  names like "Test Patient 001", MRNs that are clearly sequential test
  values, addresses using reserved documentation ranges/placeholder text)

### A.2 No real identifiers, ever

Do not use real:
- Names, addresses, phone numbers, emails of real people
- Social Security Numbers, Medicare Beneficiary Identifiers, or any real
  government-issued ID format populated with real values
- NPI numbers belonging to real providers
- Real company, employer, client, insurer, or platform names anywhere —
  code, comments, docs, commit messages, fixture data, or diagrams

### A.3 Review checkpoint

Every phase's "test" and "document" steps (see `CONTRIBUTING.md`) include an
explicit check: does any new file contain something that looks like a real
name, real credential, or real organization? If unsure, treat it as a
blocker, not a nice-to-have.

## Part B — How the platform governs data (product behavior)

This is the governance model the platform itself implements, as it is built
out phase by phase.

### B.1 Classification model

Every column of every known source dataset is classified into one of four
tiers, tracked in the metadata plane's classification store:

| Tier | Definition | Example | Handling |
|---|---|---|---|
| **Direct identifier** | Uniquely and directly identifies a person | Name, SSN, MRN, email | Always masked/tokenized; never appears in a lower environment in original form |
| **Quasi-identifier** | Not unique alone, but re-identifying in combination | ZIP code, date of birth, sex | Masked or generalized depending on policy; combinations are risk-assessed together |
| **Sensitive clinical attribute** | Reveals sensitive health information | Diagnosis code, mental health note, substance-use flag | Handled with extra care even after masking of identifiers — some policies require synthetic replacement rather than masking, given the sensitivity of the *fact*, not just the identity |
| **Non-sensitive** | Neither identifies nor reveals sensitive information | Encounter type code, currency code | Passed through unmodified |

Classification is produced by the discovery engine (rule-based + pattern
detectors) and always has a confidence score and a human-confirmable status.
Nothing is treated as "safe to leave unmasked" purely on an automated
classifier's say-so below a configured confidence threshold — low-confidence
columns default to the more conservative tier until a data steward confirms.

### B.2 Masking policy

A masking policy maps classification tier → transformation:

- Direct identifiers → deterministic pseudonymization/tokenization (same
  real value always maps to same token within a defined scope, enabling
  joins without exposing the real value)
- Quasi-identifiers → generalization (e.g., date of birth → birth year, ZIP
  → 3-digit prefix) or deterministic masking, depending on policy
- Sensitive clinical attributes → either masked in place (least disruptive
  to referential/analytical shape) or replaced with synthetic equivalents
  (when the policy decides the *fact itself* is too sensitive to carry
  through, even de-identified — e.g., certain behavioral health or
  substance-use indicators subject to extra regulatory protection)
- Non-sensitive → pass-through

Policies are versioned; every job run and every snapshot records which
policy version produced it.

### B.3 Certification

A dataset is not published for consumption until it passes certification:
automated checks that verify (not merely assert) that the masking policy
was actually applied — no raw values from the direct-identifier tier appear
in the output, referential integrity holds across the expected key
relationships, and distribution/volume shape is within tolerance of the
sizing rule. Certification results are themselves durable, auditable
evidence.

### B.4 Access control

Access to request or view data is scoped by classification tier and by
environment. A role that can request a subset for a "quasi-identifier only"
tier is distinct from a role that can request one that includes sensitive
clinical attributes, even after masking — because governance in a regulated
environment cares about *purpose and minimum necessary access*, not only
about whether data happens to be de-identified.

### B.5 Retention and refresh

Snapshots have an explicit expiry/refresh cadence tracked in the metadata
plane. Stale snapshots are flagged for refresh or deletion — this is both a
data-quality concern (stale test data drifts from production shape) and a
footprint-management concern (unbounded snapshot retention is a real cost
and a real risk surface).

### B.6 Audit evidence

Every governance-relevant action — classification confirmed/changed, policy
approved/changed, dataset requested, dataset published, certification
passed/failed, access granted/revoked — produces an immutable audit event.
This is the evidence an auditor or compliance reviewer would need to answer
"prove this dataset was handled correctly," and it is treated as a
first-class deliverable of the platform, not a logging afterthought.
